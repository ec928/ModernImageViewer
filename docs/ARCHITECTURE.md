# ModernImageViewer architecture ledger

Authoritative invariants. Consult this before changing decode, cache, or GPU lifetime. Update it when those rules change.

## Product

Unpackaged WinUI 3 / Win2D image browser (portable zip). The in-app cinematic director is an in-tree beta surface, not described as a core README feature. Collage work happens in Multi-view. The separate Collage editor was removed on 2026-10-31.

Local state lives under `%LocalAppData%\ModernImageViewer\` (`settings.json`, cinematic window bounds, `CinematicAutoSave.json`). Never `ApplicationData.Current` — this app has no package identity. `settings.json` and the autosaves are written through `AtomicFile`, and saves of `settings.json` run one at a time. A file that cannot be read at start is kept as `settings.json.unreadable` before defaults take over.

UI/UX styling, typography, theme parity, and component specifications are documented in `UI_UX.md`.

## Decode tiers

| Tier | Max edge | Who | GPU? |
|------|----------|-----|------|
| Thumbnail | tile size on screen, 250 to 1024 (`ViewerMath.ThumbnailEdge`) | `ImageItem` (shell thumbnail, WIC fallback) | No |
| Fast preview | 1200 | `ViewerEngine.DecodeFastPreviewAsync` | Uploaded on UI thread |
| Viewer, fit | long edge of the view | main window and detached window, after the preview | Yes |
| Viewer, zoomed past fit | native, capped at 16384 | same windows, one further decode | Yes |
| Display / cinematic | 4096 | `SceneAnalysisService` | Yes |
| Export | sized to the cell | Multi-view export | Temporary, disposed after save |

`DecodeHighFidelityAsync(path, token, maxEdge)` is the viewer decode past the preview. `maxEdge` is the long edge to produce, never above 16384. At fit that edge is the view. Zoomed past fit it is the file, capped at 16384. The scroll wheel's lower limit stays 0.1 for an ordinary photo. Fit of a wider image may go below 0.1, and that fit becomes the wheel floor for that image only.

WIC color-manages to sRGB, so the draw path has no color management of its own.

`.tif` and `.tiff` use that same decode. A multi-page TIFF shows its first page. A frame count above one is played only for other files, which is the GIF path.

## Image cache ownership

`ImageCache` is the only writer of the shared decode cache.

- `Publish(path, entry)` — cache takes the entry (initial refcount 1). Releases any *different* previous occupant. Will not replace a longer `DecodedLongEdge` with a shorter one (a high-fidelity entry still beats a preview when an edge was not recorded). Uses `TryRemove`/`TryAdd`, never a raw indexer write.
- `TryGet` — borrow. A surface that draws an entry must `AddRef` for the time it holds GPU pointers (`ImageViewerControl.InjectImage`) and `Release` in `PrepareForNewImage` / Unload / device-lost.
- `Evict(path)` — `Release` + remove. A detached window that displays a cache entry keeps it alive via the control’s `AddRef` until it `Release`s. Closing the window cancels an in-flight decode and releases that entry if it has not been published.
- `Rename(old, new)` — move the slot; release anything displaced at `new`.
- Never `dictionary[path] = entry`. Never `Dispose()` GPU fields on a shared entry. Device-lost: `ImageCache.Clear()` (including GIF `AnimationFrames`) and re-decode. Treat animation-frame device mismatch like `GpuBitmap` mismatch.

Refcount: cache hold = 1. Detached windows `AddRef` when they display a cache entry and `Release` on close. The main window counts them by window (`_detachedWindowCount`), and closing it only hides it until the last has gone. A detached window opens fitted and stays fitted through resizing, as the viewer does, until it is zoomed. `ManageCache` `Evict`s keys outside the keep-alive radius (current ± 20). Prefetch is current +15 / −8.

GPU objects (`CanvasBitmap`, `CanvasRenderTarget`, Win2D effects) are created and disposed on the UI thread that owns the `CanvasDevice`.

## Folder scan

`ScanFolder` increments `_currentScanId`. Every UI marshal that mutates `Images` must capture that id and no-op if it no longer matches. A new scan may `Images.Clear()` only after in-flight batches have been dropped (they check the id).

The file list is one enumeration. `AddRange` reports each appended item. It does not raise `Reset`, which recycles the visible rows and restarts their thumbnails on every batch.

A scan asks whether the folder exists off the UI thread, because an unreachable network path blocks for about 33 s. The Recent menu and the Save/Load menu do the same and redraw when the answer changes; Save/Load waits at most 60 ms first, so a folder that answers at once shows its layouts without a jump. The check that follows a click goes through `_scanRequest`, so a later request wins. A scan that fails sets `_scanError`, which the empty state shows. It never lets an exception out, because `App` does not recover from unhandled ones and async void callers would close the app.

A debounced `FileSystemWatcher` on `_currentDirectory` runs `RefreshFolderInPlaceAsync` when the grid is showing (preview closed). It merges the new list into `Images` (`ListMerge`), so the selection, scroll position, cursor and other thumbnails stay. F5 is the full `ScanFolder`. Events while the preview is open or a scan is running set a dirty flag and run when the preview closes / the scan finishes. A rename is dirty if either the old or new extension is supported.

## GIF compositing & Animation Playback

Multi-frame decode reads `/imgdesc/Left`, `/imgdesc/Top`, `/grctlext/Delay`, `/grctlext/Disposal`. Frames are composited onto a canvas sized to the (possibly 16384-clamped) logical screen, not each frame's bitmap size.

Disposal: 0/1 keep, 2 restore background (punch frame rect), 3 restore to previous (snapshot before draw).

Every frame is held whole on the GPU, so `ViewerMath.AnimationBudget` caps an animation at 2 GB: smaller first, down to half size, then the first frames only, with a HUD message.

**Animation Engine**:
- Animated GIFs (`.gif`) bypass the 1-frame fast preview tier and decode directly via `DecodeHighFidelityAsync` so `AnimationFrames` are ready on open.
- When `AnimationFrames` contains multiple frames, `ImageViewerControl` activates the animation HUD (`[◀] [⏸] [▶]  1 / N`). Space toggles play/pause; Left and Right navigate individual frames.
- MultiView cells and Solo view explicitly enable `BitmapImage.AutoPlay = true` for hardware-accelerated animated GIF display on the canvas.

## Threads

- Directory enumeration and WIC decode: thread pool (`Task.Run` + `AsTask(token)`).
- `CanvasBitmap.CreateFromSoftwareBitmap` / `FinalizeHighFidelityGpuResources`: UI thread with a live `CanvasDevice`.
- Cancellation: `_currentImageLoadId` / `_currentScanId` plus `CancellationTokenSource`. Prefetch must always remove `_activeDecodes[path]` in a `finally` on the UI thread.

## Versioning and release

`<Version>` / `<AssemblyVersion>` / `<FileVersion>` in `ModernImageViewer.csproj` are the single source of truth. Bump them in the same commit as the release tag, so the tag, the zip name (`ModernImageViewer-vX.Y.Z.zip`) and the exe's file properties all agree. `Package.appxmanifest` carries the same number for tidiness only — this app is unpackaged (`WindowsPackageType=None`), so nothing reads it.

`publish.bat` is the supported ship path. It publishes self-contained x64 loose files to `bin\`, copies `LICENSE` and `README.md` in, checks `System.Private.Xml.dll` is full size (a part-installed SDK yields a build that compiles but crashes on launch), then smoke-launches the exe. Do not ship a zip that skipped the smoke test.

Tests live at `tests\ModernImageViewer.Tests` **inside** the repo. `ViewerMath.cs` is linked in by source rather than by project reference: the app targets `net8.0-windows10.0.19041.0` with WinUI, which an ordinary test project cannot reference. Keep pure geometry in `ViewerMath` so it stays testable.

## Cinematic direction

Product proposal (what is built is listed in its section 2): `CINEMATIC_PROPOSAL.md`. The window is split into `CinematicWindow.xaml.cs` (window, keys, chrome), `.Playback.cs` (decode, clock, draw), `.Edit.cs` (Edit show) and `.Music.cs`. Edit show draws over a full-window canvas, so the shot keeps the shape it plays at, and the picture being framed stays clear of the panel and strip. Bar is **excellent cinematic in this app**: directed Play on a filled show, optional Edit show, music, present. VideoDirector remains the compositor / MP4 export app.

Slide length and no-repeat live in `ShowPacing`, and `CameraFraming.KeepCovered` keeps an Auto frame over the whole screen; both are plain maths with tests. A slide duration of 0 means Auto. `MusicBed` is the player Cinematic and Surprise me each own, and `MusicLibrary` reads ratings from tags directly, because Windows' own rating loses half-stars. Songs open as `StorageFile`, because the player cannot resolve a `file:` address with non-English letters in it. A folder is scanned in random order, so the first qualifying song is random and starts at once. A new Play from the grid or viewer starts from the launch list. `CinematicAutoSave.json` is a crash restore only: written atomically while a show is open, deleted on clean close of the last cinematic window, offered once on the next Play if the file is still there.

## Multi-view

Multi-view is cell based, not multi-image. A freeform cell is a cell that can also be moved and resized and sits at a high z-index. `CreateCell` builds both kinds, and both are indexed by `_items` and `_cellRoots`. A freeform cell is hosted on `FreeformCanvas` and is not in the `MosaicLayout` tree, so `GridCellCount` leaves it out.

A cell holds the parameters that are applied to its content, and the content is the image. By default, copying an image changes only the target cell's content: the target keeps its parameters and applies them to the new image. A swap exchanges content in the same way.

Copy and swap can also include the cell's attributes, from the second column of their menu (`CopyCellAttributes`, `ExchangeCellAttributes`). Attributes are the frame, the image's turn and flips, and zoom and pan. The window part of `CellGeometryDto` (shape, its flips and rotation, `ImageCounter` and the L's corner) moves only between two floating cells: export and `CoverBox` read a grid cell's geometry as they read a floating cell's, so a grid cell must stay a rectangle. Place, size and layer belong to the cell and never move. The values are cloned, so the two cells stay independent. Alt+drag remains content only.

A floating cell draws its shape and frame from `FreeformCard.Item`, so that must point at the new `ImageItem` before the cell redraws. Copy once set it afterwards, and the redraw read the old item, which has no parameters left after `MoveCellParameters`: the target drew as a plain rectangle while its stored frame and shape were intact.

Triggering Freeform always generates a new cell, whatever other cells exist or show: the existing cell is left empty, and the new cell has the image, a clone of the existing cell's parameters and the highest z-index, so a 4-cell view becomes a 5-cell view. The new cell is independent: changing it does not change the existing cell.

A picture dropped from outside the app also generates a new floating cell, but it has no source: no other cell changes, `SourceSlot` is -1 so Dock gives it a new grid cell, and it starts with default parameters and the highest z-index (`AttachFileDrop`, `AddDroppedPicturesAsync`). Its size follows the picture's shape, read from the file header, up to 45% of the canvas in each direction. One drop adds at most `MaxDroppedCells`. The handler sits on the control's `RootGrid` and marks the drop handled, or the main window's own drop would replace the session. A drop with no pictures goes on to the main window (`OpenDroppedItemsAsync`), and so does any drop during an Alt-drag swap or Solo.

The Add images button parks the session while the user finds pictures with the app's own navigation. The window stays at the layout's size while parked (`_parkKeptSize`), and the gallery's own size stays stashed until the session is left. Coming back makes each selected picture a new floating cell, as a drop from Explorer does (`AddPicturesAsync`). Add image on an empty cell parks the same way with that cell as `_parkedCell`, and the first picture clicked goes straight into it (`FillCell`). An Explorer drop onto an empty cell fills it with the first picture (`EmptyCellAt`); only the top cell at the point counts.

An empty cell is a cell whose `ImageItem` has no path (`IsEmptyCell`, `EmptyCell`). It holds no image, keeps its parameters for the next image, draws nothing but a label that fades with the playbar, leaves the canvas showing in an export, and is saved in a layout with a blank path. Freeform and Clear cell make one. Layouts saved when cells could be hidden load those cells as empty, including a hidden cell whose photo was not in use elsewhere.

Going back to the grid deletes the extra cells and resets cell parameters. Grid Layout, and its keys, need at least two grid cells that show an image: empty cells and freeform cells do not count.

Each cell has its own `ImageItem`, and `_itemBorders` and `_cellGeometry` hold its frame and turns against that object. When the image changes, `MoveCellParameters` or `ExchangeCellParameters` carries them over, so they stay with the cell. Docking returns the image to its source cell while that cell shows no image, and otherwise adds a new grid cell. `FreeformCard.SourceSlot` is still an index. `RemoveItem` keeps it correct. `SpawnFreeformCell` clones the frame and the image turn, while zoom and pan start at default.

A floating cell can move and resize until its centre reaches the canvas edge (`FreeformBounds`). The centre is the limit because a cell turns about it, so the limit is the same at any rotation and for any shape. Limiting the rectangle stopped a turned cell at an edge that was not on screen. A new cell, from Freeform or a drop, still starts fully inside. `FreeformCanvas` is clipped to the canvas (`AttachCanvasClip`), so what hangs over is cut on screen as it is in an export, and cannot cover the title bar or take its clicks.

A floating cell keeps its place and share of the canvas when the canvas changes size, as a grid cell does (`RescaleFreeformCards`), so a change of shape also changes the cell's shape. A layout file records the canvas size it was saved on, and its floating cells are scaled to the canvas it opens on. A file with no size is taken as the current canvas.

The canvas is `RootGrid`, not `CellsGrid`. The canvas frame (`_canvasFrame`, `ApplyCanvasFrame`, saved as `canvas.frame`) moves `CellsGrid` in by its gutter plus line, so the line never covers a photo. From the outside in the order is gutter and mat, line, grid, the same as a cell. Exports and the canvas label measure `RootGrid`, and grid cells are placed relative to it. The mat and line sit behind the grid and floating cells sit above them, the same order the export draws. As in a cell, the canvas and mat stay square and only the line and what is inside it round: a composition clip keeps the grid inside the rounded line. The mat is a whole-canvas fill with the line's shape cut out, and the shadow the grid and line cast onto the gutter is an image on that same layer. Every frame shadow is drawn small and stretched (`FrameShadow.Downscale`), with the card's hole cut at full size by a clip, on screen and in an export. On screen it is drawn again only when its key changes. A 7680x4320 canvas shadow took 38 s in a Debug build before this and takes under 70 ms after. The export puts back what grid cells covered past the line, draws the line, then the floating cells.

A file that will not open marks its cell `Failed`. The cell says so by name, export carries on without it, and it stops counting as still loading (`AnyPhotoLoading`). A photo waiting off screen past the 16-photo limit has no cell and does not count either. A layout tree that does not place each photo exactly once falls back to the plain layout (`MosaicNodeDto.FitsPhotos`).

The Advanced menus are in `MultiViewControl.Advanced.cs`. Every cell can replace its image with one picture found in the app, the same way Add image fills an empty cell (`FillCell`, `ReplaceCellImage`), which is a change of content like any other: the cell keeps its parameters, and a `Failed` cell recovers when the new file loads. Every cell can rotate its image in quarter turns and mirror or flip it. Every cell can take a window shape (`WindowShapes`, `ApplyCellShape`) and mirror or flip it. A freeform cell can also rotate the window from the menu in 15 degree steps or with its drag handle, and move the L's inner corner with its handle. Its layer among the floating cells is set from the menu; clicking a floating cell does not raise it, so a chosen order holds. A dragged floating cell snaps to the canvas, other floating cells and showing grid cells (`FreeformSnap`); Alt turns that off. The playbar's Advanced button holds undo, redo and Fill or Fit. Its Canvas button holds the canvas aspect ratio, surface and color (`CanvasLook`), which show wherever no cell covers the canvas, and in the export. Save/Load holds copy to clipboard.

The shape clip goes on the mat and the card, never on the window: a composition visual on the floating window stopped it taking pointer input. A shaped window's photo grid has no background, and a filled polygon inside it is the area that takes pointer input, so clicks in the empty part reach what is behind. A grid cell has nothing behind it, so it keeps its background and its whole rectangle takes pointer input. The window's resize handles stay on its rectangle, so on a shape they can sit in empty space. While the pointer is over a floating cell of any shape, a grip marks each corner (`MakeResizeGrip`) and a dashed outline marks the rectangle. On every cell the hover buttons and position label sit on the cell root, outside the clip. On a floating cell the label is centred and stays upright (`ApplyWindowTurn`). The rotate and L-corner handles and the hover buttons stay for `WindowHoverGraceMs` after the pointer leaves, because they can sit outside the shape. A shaped window turns off the card's rectangular stroke and draws its frame along the outline, pulled in by half the stroke so it is not cut at the photo's edge. `ApplyBorderToCell` reapplies the outline, so it follows every frame change. The gutter moves every edge of the shape inward by the same distance (`WindowShapes.Placed`): the mat fills the outer outline, and the photo and frame sit on the inner one. Outlines are polygons in a unit square, with curves as many short edges, so a new shape needs only its points. Corner radius rounds the corners of any shape that has them; the oval, squircle and blob have none (`HasNoCorners`). A gutter too big for the shape is reduced until it fits (`WindowShapes.Inset`): a shape inset past its middle comes out upside down with its area sign unchanged, so reversed edges are the test (`TurnedInsideOut`). The shadow is cast from the inner outline onto the mat (`FrameShadow.RenderAlpha` with an outline), and `ApplyShapedShadow` renders it again only when something it depends on changes. Rim glow belongs to rectangles, so a shape keeps its shadow whichever is chosen. On screen every shadow renders at half size and stretches to fit (`ShadowPreviewDivisor`), because it is soft and a full-window render took over 300 ms on every drag step. Export renders at full size.

Rotating the shape alone turns the window one way and the photo the other (`ImageCounter`), so the photo holds still on screen. Hold Ctrl on the rotate handle. In Fill the photo grows only enough to cover the shape (`WindowShapes.CoverBox`).

Undo (`MultiViewControl.Undo.cs`) keeps whole-session snapshots in the layout file format. After a pointer release, wheel, key or closed menu it compares the session with the last snapshot, so anything saved in a layout is undoable with no extra code. A restore rebuilds the cells and hands them the images already decoded. Snapshots hold floating cells as shares of the canvas, so the window's size is not part of undo. Until something has been changed, the starting snapshot follows the canvas (`RebaseUntouchedUndo`), because a session can open before the canvas has its size.

Solo follows the cell's quarter turns and mirroring with `SoloTurn` on the image, and zoom and pan on its host, so panning follows the screen. Stepping through Solo skips empty cells.

Move to is a copy followed by emptying a grid source or closing a floating one (`MoveItemTo`). Each row of Swap with, Copy to and Move to is one `MenuFlyoutItem`, retemplated to draw two cells (`MakeCellTargetMenu`, `CellTargetRowTemplate`), because a menu cannot lay its entries out in columns. The menu handles the click, and where the pointer sits in the row picks the column; the Left and Right keys pick it from the keyboard. Do not put buttons inside a menu entry: the first version did, and its clicks failed for the mouse while touch worked.

Strokes, gradient ends and mats share one set of swatches (`FramePalette`), and a test fails if any two in it, or in the canvas list, come too close. The last swatch, and Custom in the canvas menu, open the standard Windows color dialog (`WindowsColorDialog`). It has no transparency, and its custom slots last until the app closes. Leaving Multi-View by Back, Esc or the tile and list buttons does not clear the session: `CloseMultiView` collapses the control and sets `_multiViewKept`, and the Multi-View button resumes it, undo history included. Choosing photos with View Together or opening a layout replaces it. It is not kept when the app closes. Reset canvas and images in the wheel replaces the session in place with four empty cells, as one undo step (`ResetCanvasAndImages`). `AutoSaveSession` keeps the last three sessions in `autosave` beside the settings, in the undo snapshot format, when a session is left or replaced and when the app closes. It skips blank sessions and repeats, and Save/Load lists them. A crash writes nothing, so work since the last leave is lost.

**Surprise me.** `LayoutComposer` is pure: given `PhotoFacts` and a canvas size it returns a `Composition`, which writes an ordinary `MultiViewLayoutFile`, so saving, undo and editing need nothing new. Each recipe is one design. A recipe settles its look, builds 48 versions, and `Judge` scores them; versions that cut a face or bury a picture are not chosen unless nothing else exists, and then the next recipe is tried first. Grid recipes search binary trees of cuts whose shape matches the canvas when each picture keeps its own shape, so pictures barely crop. `PhotoFactsReader` reads with `Windows.Media.FaceAnalysis` from a 1280 px decode; four readers run off the UI thread, each with its own detector, and `MultiViewControl.Surprise.cs` keeps results per path for the life of the control. `SurpriseOptions` holds the card's ranges, thresholds and odds, saved in `surprise-options.json`; damaged values fall back to the default and out-of-range ones to their limit. Nothing there can rule a design out: `Compose` orders designs by a weighted race, so a favoured one comes first more often and a rare one still can. Zoom is applied in `AimAtSubject`: the box around all faces found fills `FacesFill` of the cell, within the chosen most and `MostEnlarged` times the picture's pixels, and judging then sees the zoomed picture. `Presence` lowers soft and dark pictures, using sharpness and brightness from the reader, and raises featured ones, so the hero and the largest cell go to good pictures. `LooksLikeScreen` and `LeaveOutScreensAndRepeats` apply only to sets over 16, never to pictures chosen one by one. Each layout, by click or auto-play, is one undo step, taken after its pictures have loaded. A cell does not clamp its pan until the picture has decoded: before that its shape is a guess of 16:9, and clamping to it wiped saved framing, on Surprise me layouts and on restores alike. A picture slower than that wait can still move the framing after the step is taken, so Undo and Redo re-take the step once the restored layout has settled; otherwise the moved state is recorded as a new step, the next Undo removes it, and Undo never gets past it. Auto-play lays a clear shield over the canvas so the click that stops it does not also open a picture, and covers the canvas with a picture of itself until the new pictures have loaded, then fades it away. A session with more images than a click may use is dealt from a `PictureDeck`, in folder and date order so a hand can come from one occasion. `MatchSession` brings it into line with the session at every click, tray included, so an image the user removed stays out and an image added comes up soon; every other image goes in the tray of the layout that is made (`WithRestInTray`), which is what stops the set shrinking to what is on screen. A picture the reader cannot open is arranged by its shown size, and one already showing as failed sits out. Applying goes through `ApplyLayoutFile` with `_restoringUndo` and `_reuseBitmaps` set, as an undo does, so it is one undo step and nothing decodes again.

**Camera motion.** During auto-play the layout moves as one picture, planned by `CameraMove`, which is pure and knows nothing of drawing, and floating cells take their own `CellFloat` on top. `MultiViewControl.Camera.cs` applies this each frame on the composition visuals, through `TransformMatrix`, never on XAML. That is load-bearing, for reasons found by running it: a `RenderTransform` that changes every frame left images soft and cost about three times the CPU; `UIElement.Rotation` and `Scale` stop the app on an element with a `RotateTransform`, as a tilted floating cell has; and XAML keeps that `RotateTransform` in the same `TransformMatrix`, so a floating cell's matrix must include its saved turn. The cover over a layout change is rendered from the control rather than `RootGrid`, because a zoomed layer overflowing the element being rendered makes the bitmap larger than the canvas. To test motion, compare a paused layout with the same layout re-applied by Undo and Redo, and use a layout with tilted cells.

Rows and Columns are a switch on the playbar (`CountsSwitch`). Hero is a row in the same card (`BuildHeroRow`), because it is a choice of layout too; H still steps through the kinds (`CycleHero`). The Grid layout card is a plain panel above the bar (`CountsCard`), not a flyout: a flyout dismisses itself on any outside click, and that raced with the switch reopening it, so the card sometimes failed to open. Only `OpenCountsCard` and `CloseCountsCard` change it. A press outside the card or switch closes it, and Esc closes it first. The frame card closes while the dialog is open and comes back with its settings (`ReopenFrameCard`). The card is placed by a point in the window (`FrameCardPosition`): beside its cell when there is room, otherwise against the window edge farther from the cell. A placement relative to the cell squeezed the card into whatever space was left, and with a large floating cell that cut it down to a few rows. Presets are Flush and three frames saved by holding the button, kept in `settings.json`.

Known limits of this prototype. Snapping uses a rotated cell's unrotated rectangle. Solo shows the image's quarter turns, not a shape-only turn. A cell's zoom and pan are in pixels, so they are clamped rather than scaled when the canvas changes size.

The layout is a `MosaicLayout` tree of row and column splits; a leaf is a photo's index in `_items`. `MosaicLayout.ShownCount` is the one place the 16-photo limit lives. The image tray is the grid slots past those on show (`_framedSlots`, `VisibleCount`, `TrayImages`), so saving and Undo carry it with no extra code, and the playbar counts both, as `16 on canvas, 7 in tray`. `MosaicLayout.PlaceAdded` is the rule for where added images go. Positions shown to the user skip the tray (`PositionOfSlot`). Grids come from `FromCounts` (photos per line), Banner and Pair from `CreateHeroLines` (the hero plus the other photos in lines), and Rectangle from `CreateRectangleHero`, which is drawn by hand for 4, 5, 6, 7 and 9 photos only.

The multi-view root forces Dark, so the photo canvas and playbar stay dark in a light window. The grid-layout card and its flyout presenter are pinned to Dark as well (`ApplyGridLayoutTheme`), to match the playbar.

Cells are owned by slot: `_cellRoots[i]` is the cell showing `_items[i]`. A swap leaves the cells in place and moves the decoded images between them, so no photo decodes again and dragged sizes stay. A photo still opening, or waiting off screen, has nothing to move and loads into the cell instead. Removing a photo also keeps the other cells: its root is dropped, its entries leave the shared lists through the `CellParts` on its `Tag`, and the layout is rebuilt for the new count with `_relayoutKeepingCells`; only a photo past the limit that moves into view decodes. Because a cell outlives a swap, its controls (move arrows, menu, maximise, drag) look up `Slot(item)` when used; never capture the index at creation. Save JPEG reads cell `i` from `_cellRoots[i]` for the same reason: the order cells are built in follows the tree, not the photo order, and differs for a hero on the right or bottom.

Changing the line count, a line's count or the hero builds a new layout and resets dragged sizes, but keeps the cells (`RelayoutKeepingCells`), so nothing decodes again. The rows/columns switch turns a plain grid or a Rectangle a quarter (`Transpose`) and keeps dragged sizes; beside a Banner or Pair it relays the other photos.

Never close a thumbnail's `SoftwareBitmap` after `SetBitmapAsync`, and never dispose its `SoftwareBitmapSource`. Closing the bitmap when the call completed caused a crash when switching between the tile grid and Multi-View: WinUI failed fast in `AsyncCopyToSurfaceTask::CopyOperation` on a background thread, with RO_E_CLOSED on the stack and nothing in `crash.log`. WinUI most likely copies from the bitmap again after the call completes, such as when a tile is recreated during a resize. The source can be on screen in several places at once: its tile, a cell's placeholder, the viewer and the preview. Both are left to the garbage collector. A native fail fast like this leaves a dump in `%LocalAppData%\CrashDumps`, and Microsoft's public symbols for `Microsoft.UI.Xaml.dll` name its stack.

A cell's grid thumbnail is only a placeholder: it is removed when the photo loads, and `CellParts.Photo` names the photo's `Image`. Save JPEG takes each photo's native size from that `Image`; reading the first `Image` in the cell found the ~250 px thumbnail and capped the export at thumbnail resolution.

### Storyboard, Camera Director and Undo

- **What Play plays.** `PlayUsesStoryboard` is true while a storyboard plays (`_isStoryboardPlayback`), or when a storyboard has scenes and Auto-Mix has not been chosen (`_shuffleChosen`). The bar's switch sets it, and so do the ways of playing the storyboard (Play Show, a card's play button, Play show from here), making a show, adding a layout as a scene, clearing a storyboard and opening one. Opening the drawer, choosing its tab, clicking a scene card and Camera Director do not.
- **Storing the canvas into a scene.** `SyncCanvasToSelectedScene` writes the canvas into the selected scene only when that scene is the one on the canvas (`_canvasSceneId`, `ShowProject.ShouldStoreCanvas`) or when asked (Update scene from canvas, on a card's menu). Card drops, freeform resizes, turns and splitter drags store it, and so do play, pause and leaving a scene. A store that would change nothing leaves the scene and the show untouched, and the scene keeps its own creation time. Both are load-bearing: Undo compares whole sessions, show included, and a store that stamped `Modified` or a new `Created` made every Undo press take a new step and undo only that one, so Undo did nothing while a scene was on the canvas.
- **Undo and the storyboard.** Undo snapshots carry the storyboard (`BuildLayoutFile` sets `Storyboard` when it has scenes). Restoring one without a storyboard clears the show (`RestoreSnapshot`); loading a layout does not, because Auto-Mix and scene previews load layouts too. A change to the list of scenes (remove, duplicate, move, drag) is an Undo step through `NoteUserAction`, taken once the selection has settled. A removed scene stops being the selected and on-canvas scene, or every later step would store the canvas into it. Make a show and Replace show take their step when the show is made, because the click's own step was taken while it was still being made. Redrawing the open drawer after a restore counts as a closed menu, so that timer is stopped, or Redo would be cleared.
- **Growing a show.** Add new layout drafts one scene with `ShowDirector.DraftSceneAsync` from `ShowProject.ImagesNotInShow`, the images no scene uses, in pool order, and from the whole pool once there are none. It shares `BuildScene` with Make a show, so its hold, transition and face-aimed camera path are made the same way. The toolbar's Update scene was removed: with a scene on the canvas its edits are already stored, so it nearly always had nothing to do.
- **Empty cells in scenes.** A scene of floating prints has one empty grid cell under them. Storing the canvas keeps empty cells (`p.Slot < onShow`, path or not), and `MultiViewLayoutFile.WithPoolAfter` gives a layout with no grid slot an empty one before it appends the pool. Before, storing dropped the empty cell, so the next time the scene was shown the first pool image took slot 0, showed behind the prints, and was then stored into the scene. Scenes stored that way before the fix are repaired as they are shown: the empty cell comes back and the pool stays off the canvas. A pool image already stored into a scene stays until it is removed.
- **Single images.** `LayoutComposer.ComposeSolo` picks fill, matted or whole with `SurpriseOptions.PickSolo`, from three odds (`SoloFillOdds`, `SoloMattedOdds`, `SoloWholeOdds`, default 2, 1, 1). Fill is never picked when it would show under 65% of the image or cut a face.
- **One generator, named overrides.** The Layout Generator (`LayoutComposer` and `ShowDirector`) has one set of settings, `SurpriseOptions`, saved in `surprise-options.json` and edited in Layout Generator Settings. `CinematicOverrides`, its `Cinematic` property, saved with the rest, holds the few settings Cinematic storyboard puts in their place. `SurpriseOptions.WithOverrides(name)` returns a copy with them applied and leaves the saved settings alone. A show records the overrides it was made with in `ShowProject.GeneratorOverrides`, and `MultiViewControl.GeneratorSettingsFor(show)` gives the settings for it, used by Play storyboard, Cinematic storyboard, Add new layout, Replace show, the drawer's images-per-scene picker and storyboard playback. Clear sets `GeneratorOverrides` back to null. Another set of overrides is another class like `CinematicOverrides` with a name, never a second generator or a second full copy of the settings.
- **Transitions.** `SurpriseOptions` holds four odds (`CrossfadeOdds`, `ZoomThroughOdds`, `ThroughDarkOdds`, `SlideOdds`) on the designs' scale. `LayoutTransitions.Pick` rolls them, leaving out the kind just used unless it is a crossfade; `LayoutTransitions.Shares` gives the long-run mix the settings show, with a damped iteration so a mix where kinds alternate still settles. A saved `TransitionVariety` (the earlier single slider, which capped the other kinds at 7 in 10) is converted once by `OddsFromVariety`, a search for the odds whose shares match, and not written back. Storyboard playback passes each scene's stored `Transition` to `ChangeLayoutOver`; before 0.30.7 it rolled a new one from the current settings, so what a scene stored never played. Cinematic overrides do not include transitions.
- **Smooth playback.** Measured 2026-11-04 with a temporary frame probe (removed), a Cinematic storyboard of 122 images on a 144 Hz screen. Three causes, three fixes:
  - The camera ran on the UI thread, a transform set each frame, so any UI work held it still. `AnimateCamera` now samples the move 30 times a second into compositor keyframes (zoom with the turn's extra, pan, angle in a `CompositionPropertySet`), and each camera layer's `TransformMatrix` is an expression of them with the layer's own offset. The compositor's thread keeps the camera moving through UI work. The per-frame handler only drifts floating cells. A resize re-samples from where the move is.
  - The storyboard built all its scenes in the first seconds of play, each one UI work: about 1 frame in 30 ran 25 to 50 ms. While playing it now stays `ScenesAheadWhilePlaying` (3) ahead, woken at each change of scene (`_storyboardAdvanced`); the summary and badge wait for a pause (`CatchUpStoryCounts`).
  - Each change of scene held the old picture still for 140 to 180 ms: a snapshot of the canvas (about 28 ms), the new layout (about 20 ms) and up to 120 ms waiting for its images. The next scene's images are now decoded while the current one holds (`PreloadStoryScene`, as Auto-Mix's `PrepareNextSurpriseAsync` does), and `WaitForPicturesAsync` waits for loading and one drawn frame instead of a fixed 50 ms. The pause is now about 45 ms, the snapshot and the layout.
- **Camera moves.** A `CameraMove` is a list of `CameraShot`s (from, to, share of the time, `CameraCurve`, bow); a shot whose start is not the last one's end is a cut. `CameraCurves.Ease` holds the six curves (Smooth is smoothstep, what every move used before). `At` eases by the shot's curve, interpolates zoom by ratio, bends a pan's path by `bow` times its length at `sin(pi t)`, and interpolates the angle. `CameraView.Angle` is drawn by `ShowCameraView` as a rotation about the canvas centre in the layers' composition matrix (never a XAML transform), zoomed by `CameraView.TurnCover` = cos + sin x longer side's share, so a view the canvas covers unturned stays covered. `CameraMove.Plan` takes a `CameraStyle` (curve odds, bend range, turn range, two-shot chance, from `SurpriseOptions.CameraStyle()`); with none it is the plain one-shot Smooth move. Two-shot scenes need a face subject and 8 s. Storage: `CameraViewDto.Angle`, and `CameraKeyframeOverride.Curve`, `Bow`, `Share` and `Shots` (`CameraShotDto`, `From` null to follow on); `ToShots`/`ToCameraMove` read them, `FromMove` writes them, and anything missing reads as before. `ShowScene.Clone` copies the path through JSON, so no field is lost. Saved `MotionAmount` (main and Cinematic) becomes `MotionLeast` = `MotionMost`.
- **Pace across scenes drafted one at a time.** `DraftSceneAsync` takes the other half of the duration range from the previous scene's hold (`SurpriseOptions.WasLong`), so short and long take turns as they do in a show drafted at once. Before, each scene drafted alone picked a half at random.
- **Saved durations.** `SurpriseOptions.FromJson` keeps any whole second from 3 to 60. It used to check them against the old menu lists, so a 7 to 12 s range set on the Duration slider came back as 5 to 15 s on the next launch.
- **Play storyboard.** `MultiViewControl.MakeAndPlayStoryboardAsync` drafts one scene at a time with `DraftSceneAsync` from the images not in the show, starts `PlayStoryboardAsync` after two, and goes on until none are left. Playback reads `_activeShow.Scenes` at each step, so scenes added during play are played in turn. A ticket and the show's identity stop it when the show is replaced or cleared. The drawer keeps its own list of scenes (`scenesCollection`) and writes it back to the show on any change, so each scene the build adds also goes into the open drawer's list (`_sceneAddedBehindDrawer`); before 0.30.4 a drawer action during the build dropped every scene added since the drawer opened. `_imagesBeingDrafted` keeps the build and Add new layout from taking the same image at once.
- **Scene cards.** `ShowScene.ThumbnailBoxes` is where each image sits, as shares of the canvas: the saved split, or the rows and columns when none was saved, with floating images on top when the canvas size was saved. It is pure and tested. The card draws from it.
- **Camera Director.** A keyframe editor in `MultiViewControl.CameraDirector.cs`: Start (emerald) and End (ruby) frames with badges above both, wheel zoom from 1.0x to 2.5x and a 2.5 s preview. Done or Enter keeps the scene's path; Cancel or Esc leaves it as it was. Stepping to another scene keeps the one left. Only F1 and F11 reach the window while it is open, so Undo and Save/Load cannot change the canvas under the frames. A second Esc handler on the canvas ignores keys already handled, or it acted on the same Esc twice.
- **Files.** Storyboards are `.mivshow` (`ShowProject`), layouts `.mivlayout`. Both open from Save/Load, Explorer, the command line and a drop (`HandleFileActivation`); a storyboard opened from outside replaces the session, which goes to Autosaved. Save/Load lists storyboards first in each folder.

## Bare Alt

There is no Alt peek at the sidebar; it was removed because it fired whenever Alt was held for an Alt-drag. The bare Alt key-down and key-up are still marked handled so Alt does not move focus to the window's system menu; Alt+key combinations are unaffected because the system tracks the modifier itself.

## Name ordering

Anything that orders file or folder names for display goes through `NaturalSort`, which calls the shell's `StrCmpLogicalW` — the function Explorer's Name column uses. Ordinal comparison sorts digit runs as characters, which puts 10 between 1 and 2. Do not hand-roll a replacement: leading zeros, embedded spaces and punctuation all have to match, and any divergence is the same bug in a narrower case. `StringComparer.OrdinalIgnoreCase` stays correct for dictionary keys and path equality, which are lookups rather than display order.
